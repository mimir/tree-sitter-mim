# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A tree-sitter grammar for **Mim**, the front-end language of MimIR. The only hand-written sources are
`grammar.js` (the whole grammar), `src/scanner.c` (a tiny external scanner), and the corpus tests under
`test/corpus/`. Everything else — `src/parser.c`, `src/grammar.json`, `src/node-types.json`, and the
`bindings/` + build files for C/Go/Node/Python/Rust/Swift — is generated by the tree-sitter CLI and is
**committed to the repo**. Every grammar commit therefore also contains the regenerated `src/`.

## The spec

`docs/langref.md` in the MimIR repo is the normative surface-syntax reference and the grammar follows it
rule for rule. Where it is silent, the reference parser decides — `src/mim/ast/{lexer,parser}.cpp`,
`include/mim/ast/tok.h` (token + precedence tables) and `src/mim/ast/family.h` (token families). Read
those before inventing a rule; the precedence ladder in `MIM_PREC` and the `Prec` bound each
`parse_expr`/`parse_ptrn` call passes are what the `PREC` table here mirrors.

## Commands

```sh
tree-sitter generate          # regenerate src/ after editing grammar.js — required before testing
tree-sitter test              # run all corpus tests
tree-sitter test --file-name new.txt          # only one corpus file
tree-sitter test -i "simple group"            # only tests matching a regex
tree-sitter test -u           # rewrite expected trees in the corpus from current parser output
tree-sitter parse FILE.mim    # parse a file; exits non-zero and prints (ERROR ...) on failure
tree-sitter parse -D FILE     # write log.html with a debug graph (needs graphviz)
npm start                     # build wasm + open the web playground
```

`nix develop` provides tree-sitter (with web UI) + node + graphviz.

The system CLI may be newer than the pinned `tree-sitter-cli` devDependency (package.json). A newer CLI
rewrites the vendored `src/tree_sitter/*.h` runtime headers on `generate`; check `git diff --stat` and
don't commit unrelated churn in those headers.

## Testing against real Mim

The corpus under `test/corpus/` is small and hand-written; the real regression suite is the MimIR tree
next door. Every `.mim` file in `mimir/lit/` and `mimir/src/mim/plug/` must parse clean **except** the
six deliberately invalid programs under `lit/error/`:

```sh
tree-sitter parse -q $(find ../mimir/lit ../mimir/src/mim/plug -name '*.mim')
# expected: only lit/error/{insert_no_index,missing_name,path_member,
#           unanchored_delim,unterminated_string,where_semicolon}.mim report an ERROR
```

Run that after every grammar change — it catches far more than the corpus does.

## Grammar architecture (`grammar.js`)

### Patterns vs. telescopes

A **pattern** destructs a value (so it only appears where a body exists); a **telescope** describes a
type. The two grammars are identical except that a telescope additionally admits a bare `expression` —
hence `(a, b, c)` binds three components while `[A, B, C]` names three types.

- `pattern` — `I`, `I: e`, `(plist)`, or `p as I`.
- `telescope` — `I: e`, a bare `expression` (which covers `[tlist]` via `sigma`), or `alias_telescope`.
- `implicit` — the braced `{…}` binder; its elements are telescopes.
- `group` — `I+ ":" e`, only ever a list element. It is the one declared `conflicts` entry
  (`[$.group, $.path]`): `a b c: Nat` and `f x y` differ only in the trailing `:`.

`sigma` (`[…]`) doubles as the bracketed telescope, so there is exactly one rule for it and
`[x: Nat] → e` falls out of the ordinary `pi` rule instead of needing its own. A bare `I: e` is *not* an
expression — that is what keeps `pi`'s domain unambiguous, and why `pi` takes `expression | implicit |
alias_telescope` rather than a `telescope`.

`declaration`, `expression`, `primary_expression`, `infix_expression`, `pattern` and `telescope` are
declared `supertypes`, so they appear as hidden choice nodes rather than as named nodes.

### Precedence

`PREC` mirrors `MIM_PREC` from `tok.h`, spread out by tens so the two extra levels fit:

```
trailing(-1) < binder(1) < where < ins < inj < union < arrow < eq < rel < add < mul < shift < app < extract < lit
```

- `trailing` is below everything: a `λ`/`ret`/`match` body, a `decl_expr`'s final expression and a `Cn`
  domain all extend as far as they possibly can, so every operator is shifted into them.
- `binder` is the bound on a `typed_binder`'s type: it reaches across `→` and `where`, as it does inside
  `[…]`.
- `fn_type` is the exception that needs its domain bounded *before* the `→`, which is why it takes
  `_app_expression` instead of a full expression.

Grammar changes that "fix" one expression usually mean nudging these, not adding rules.

### `*`, `+` and `-` are operators first

`*` is both `Type (0:Univ)` and multiplication; `+`/`-` are both a literal's sign and infix operators.
The reference parser resolves this by checking for an infix operator before an application argument, so
with a left operand at hand the operator reading always wins — `f *` multiplies and `f -23` subtracts.

The grammar encodes that **structurally**, not with dynamic precedence: `star` and `signed` are members
of `primary_expression` but *not* of `_operand`, and an application argument / extract operand is an
`_operand`. `annotated` therefore must not accept a `signed` value either (that would put `+` back into
`FIRST(_operand)`); `signed` wraps `annotated` instead. `_atom` and `_app_expression` are `inline`d so
these decisions stay shift/reduce rather than reduce/reduce.

### Other things worth knowing before editing

- There is **no `%` annex sigil** any more. An annex is an ordinary member reached by a `path`
  (`core.wrap.add`); `anx` is a declaration modifier, and `anx I = path` is the alias declaration.
- Modifiers (`priv`, `pub`, `extern`, `anx`) may precede any declaration in any order, which is why every
  declaration rule starts with `repeat($.modifier)`.
- ASCII/Unicode spellings that must stay in sync: `->`/`→`, `<-`/`←`, `lm`/`λ`, `bot`/`⊥`, `top`/`⊤`,
  `*`/`★`. The delimiters `«»`, `‹›`, `⦃⦄` have **no** ASCII spelling — `<<`/`>>` are the shift operators
  and `<`/`>` the comparisons.
- `identifier` is also the escape hatch `` `op `` (`` `+ ``, `` `<= ``, …), since that is what an infix
  operator desugars to. It stays the `word` token for keyword extraction.
- Literals carry no sign at token level. `nat_literal` covers bin/oct/dec/hex; `idx_literal` is
  `23₂`/`23_2`/`23i32`; `float_literal` covers the decimal and the hexadecimal spellings.
- A literal is **not** a single token. Its marker parts are split off so highlighting can set them
  apart from the digits: `base_prefix` (`0x`/`0b`/`0o`), `idx_suffix` (`₂`/`_2`/`i32`) and
  `exponent` (`e10`/`p-3`); an `idx_literal` even nests the whole `nat_literal` as its value. The
  digit tokens themselves stay hidden. Every part after the first is `token.immediate`, which is
  what keeps the pieces glued together — `23 i32` is still an application, not a literal — and each
  prefix is paired with a digit token of its own base, so `0b19` remains no literal. `idx_suffix`
  needs its `prec(1)`: `i32` and `_2` are spelled exactly like the `i32` primitive and an
  identifier, and without it the tie on match length goes the wrong way.
- A declaration may be followed by `;` and stray semicolons are skipped, so declaration lists are
  `repeat(choice($.declaration, ";"))`.

## External scanner (`src/scanner.c`)

Deliberately minimal: two external tokens, `doc_content` and `error_sentinel`. `doc_content` consumes the
rest of the line after `///` **including the newline** (kept so markdown injection queries work);
`error_sentinel` always returns false and exists only to detect error recovery. There is no serialized
state — keep it that way unless a real need arises.

## Syntax-highlighting queries

`queries/` holds the **Neovim** queries (`highlights.scm`, `injections.scm`, `folds.scm`); `nvim-treesitter`
symlinks that directory into its parser dir, so edits are live. Capture names follow nvim-treesitter's
`CONTRIBUTING.md` - they are *not* interchangeable with Helix's, whose `.scm` files live in the fork linked
from README.md. Validate with `ts_query_ls check -f queries/` (config in `.tsqueryrc.json`; needs
`tree-sitter build` first) and format with `ts_query_ls format queries/`.

Ordering rule that bit once: when two patterns capture *nested* nodes covering the same text, the inner node
wins regardless of pattern order - that is why `anx` is captured as `(anx "anx" @keyword)` rather than as a
bare token, which would otherwise override `(modifier) @keyword.modifier`. Among patterns matching the *same*
node, the later one wins.

The literal markers (`base_prefix`, `idx_suffix`, `exponent`) deliberately use capture names that are
*not* in nvim-treesitter's list: `@number.prefix`, `@number.suffix`, `@number.float.prefix` and
`@number.float.exponent`. Each is parented on the group of the literal it sits in, so an undefined group
falls back to exactly that and the marker simply looks like the rest of the number. Defining the group
with an **attribute only and no colour** is what sets the marker apart without splitting the literal in
two: Neovim's `hl_combine_attr` keeps the foreground of the extmark below whenever the one on top leaves
it unset, so `{ bold = true }` yields the number's own colour in bold. `vim-mim`'s `plugin/mim.lua` ships
those four as `default` highlights and re-applies them on `ColorScheme`, which `:hi clear` would drop.
Colouring the size as `@type.builtin` was the obvious first idea and is wrong in practice - `23I32` then
reads as two separate tokens.

Renaming a grammar node breaks these queries and the external Helix ones.
